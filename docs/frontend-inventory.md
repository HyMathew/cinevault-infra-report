## Périmètre et provenance historique

Relevé **des sources locales du 8 novembre 2026**, sans nouvelle campagne navigateur ni nouvel appel réseau. Le précédent inventaire décrivait le commit web `4303ef3` du 7 novembre. Les ajouts de contexte client signé et de propagation de `Retry-After`, initialement relevés dans le candidat non commité, sont désormais dans le **commit web local `9b1da4f85adcd20c06e6113516de566d10aa6996`** ; le HEAD et l'absence de différences web ont été relus après cette stabilisation. Le contrat API proche correspond au commit local `4b15406c2a1125518fb9a52dc53e9f50545db28e`. Ces commits locaux ne prouvent ni publication ni déploiement ; les nouveaux comportements ne sont pas attribués au commit historique `4303ef3`.

Le frontend est un service **Flask/Jinja avec formulaires HTML**, sans SPA ni JavaScript applicatif. Le contrôle statique compte **11 modules Python dans `app/`, 28 templates HTML, 1 feuille CSS, 36 règles d'URL explicites et 33 fonctions de vue**. Trois fonctions desservent chacune deux règles : formulaire film, exemplaire et collection. Route statique Flask implicite et HEAD/OPTIONS automatiques exclus.

Les 11 règles de `app/routes.py` sont enregistrées dans les deux modes ; ses trois règles d'exemplaires renvoient explicitement 404 hors Enterprise. Les 25 règles des six autres blueprints sont enregistrées seulement avec `ENTERPRISE_ENABLED is True`. Il reste huit règles applicatives utilisables en mode pédagogique, hors statique. Un template partagé n'est pas un écran supplémentaire.

Les chemins `app/...`, `scripts/...` et `tests/...` ci-dessous sont relatifs à `cinevault-web/`. Les liens ciblent les sources réelles. L'API reste l'autorité des données, droits et transitions métier.

## Les 36 règles navigateur

**G = GET, P = POST.** Chaque mutation inclut `csrf_token`, vérifié avant la vue. Sauf précision, rendu G = HTML 200 ; erreurs API non interceptées → gestionnaire commun décrit plus bas. « Identifié » implique le hook d'identité Enterprise ; gestionnaire = manager/admin.

## Identité, sécurité et erreurs

### Sessions et CSRF

En Enterprise, install_accounts initialise g.user puis consulte `/api/v1/me` si cookie présent/syntaxiquement valide, sauf endpoints static,health,login,register. Cela concerne aussi les pages publiques avec navigateur authentifié. Cookie mal formé ou 401 profil → effacement demandé ; autre panne remonte. Une vue signed_in sans identité →303 connexion. Les contrôles de rôle web améliorent le parcours ; API revérifie droits/propriétaires.

Cookie cinevault_auth : HttpOnly, SameSite=Lax, path /, huit heures maximum. Secure suit SESSION_COOKIE_SECURE/COOKIE_SECURE : ne prouve pas que le transport courant est HTTPS. La session Flask contient le CSRF, pas le bearer ; elle est vidée à connexion réussie/déconnexion/changement de mot de passe, puis CSRF recréé au prochain contexte Jinja. POST/PUT/PATCH/DELETE comparent le jeton de formulaire en temps constant avant API ; absent/invalide →400. Corps ordinaires 64 Kio ; multipart transfert 2 Mio, lecture fichier jusqu'à 1 Mio + 1 octet.

Réponses comptes, utilisateur identifié ou cookie présent : Cache-Control no-store ; personal/lending l'imposent aussi via blueprint, export explicitement. Les pages publiques anonymes ne sont pas toutes no-store. /health reste indépendant de l'identité/API.

### Ajout du candidat du 8 novembre : contexte client signé

Sources : [`APIClient.anonymous_auth`](https://github.com/HyMathew/cinevault-web/blob/9b1da4f85adcd20c06e6113516de566d10aa6996/app/api_client.py), [`create_app`](https://github.com/HyMathew/cinevault-web/blob/9b1da4f85adcd20c06e6113516de566d10aa6996/app/__init__.py), [documentation dédiée](https://github.com/HyMathew/cinevault-web/blob/9b1da4f85adcd20c06e6113516de566d10aa6996/docs/client-context.md). **Aucun nouveau template ni nouvelle URL navigateur.** Les méthodes injectables restent `login(data)` et `register(data)` ; seul le vrai APIClient réalise la signature, sans nouvel argument imposé aux doubles injectés.

La fabrique charge la clé dédiée en bytes CLIENT_CONTEXT_KEY (prioritaire), ou CLIENT_CONTEXT_KEY_FILE ; type invalide ou <32 octets empêche démarrage. Clé distincte de session, jamais affichée. Le contrat distribué exige clé partagée web/API et CLIENT_CONTEXT_REQUIRED=true côté API ; le code local ne prouve pas la configuration déployée. Sans clé, appel JSON direct conservé pour usages explicitement choisis.

Avec clé, inscription/connexion utilisent uniquement request.remote_addr, canonisent IPv4/IPv6 et refusent zone IPv6/adresse absente ou inutilisable/contexte Flask absent par 503. **X-Forwarded-For du navigateur n'est ni cru ni recopié.** Le corps est encodé une seule fois JSON UTF-8 (ensure_ascii=False, NaN refusé) ; ces octets exacts sont envoyés. HMAC-SHA256 porte sur version protocole, seconde Unix, adresse, méthode POST, chemin et SHA-256 du corps. Headers API : Content-Type JSON, X-CineVault-Client-IP, X-CineVault-Client-Time, X-CineVault-Client-Signature. JSON impossible →422 contrôlé. Selon contrat API, signature et fraîcheur (écart maximal 30 s) sont vérifiées ; jamais en remplacement de mot de passe, bearer ou CSRF.

Le mécanisme fournit une source vérifiable aux budgets d'admission ; il ne chiffre pas le lien web–API. Horloges synchronisées et transport protégé requis. NAT réellement partagé → source partagée. Une topologie où le web observe seulement un proxy nécessite une configuration explicite de confiance ; elle n'est pas résolue par acceptation des headers navigateur.
